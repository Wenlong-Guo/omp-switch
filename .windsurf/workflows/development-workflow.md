# 开发工作流

## 使用方式

用户给出需求后，按以下步骤执行。不要跳过任何步骤。

---

## 步骤 1：生成开发计划（Plan）

根据用户需求，输出一份详细的开发计划。

计划必须包含：
- **目标**：本次需求要解决什么问题
- **范围**：哪些文件/模块会改动，哪些不动
- **技术方案**：关键实现思路
- **风险点**：潜在的坑和应对策略
- **测试策略**：新增或需要修改的测试
- **版本号**：根据变更类型确定（见下方版本规则）

版本号规则：
- 初始版本：`V0.0.0`
- **需求变动 / 新功能** → 中间位加 1：`V0.1.0` → `V0.2.0`
- **Bug 修复 / 小补丁** → 末位加 1：`V0.0.1` → `V0.0.2`

// turbo
## 步骤 2：Prompt 优化（Prompt Master）

调用 `prompt-master` 技能，对步骤 1 生成的计划进行优化：

1. 将计划内容作为输入，让 prompt-master 优化为更精确、可执行的提示词
2. 重点关注：
   - 文件范围是否明确
   - 约束条件是否清晰
   - 输出格式是否具体
   - 停止条件是否定义
3. 吸收优化建议，更新最终执行计划

// turbo
## 步骤 3：开发实施（Develop）

按优化后的计划执行开发：

1. **读代码**：先读相关文件，理解现有逻辑
2. **写代码**：实现功能，保持现有代码风格
3. **加测试**：新增对应测试用例
4. **类型检查**：确保 TypeScript / Rust 类型通过
5. **最小改动**：只做计划内的事，不额外重构

遇到计划外问题，暂停并报告用户，不要擅自扩大范围。

// turbo
## 步骤 4：自测与修复（Test & Fix）

开发完成后，执行全面自测：

**前端测试**：
```bash
npm run test
npx tsc --noEmit
```

**后端测试**：
```bash
cd src-tauri && cargo test
cd src-tauri && cargo check
```

**修复流程**：
- 记录所有失败测试和编译错误
- 逐条修复
- 修复后重新运行测试，直到全部通过
- 不要删除测试来让测试通过

// turbo
## 步骤 5：代码审查与修复（Review & Fix）

自测全部通过后，进行代码审查：

**审查清单**：
- [ ] 代码是否符合项目现有风格
- [ ] 是否有未使用的变量/导入
- [ ] 错误处理是否完善
- [ ] 边界条件是否覆盖
- [ ] 性能是否有明显问题
- [ ] 敏感信息是否硬编码
- [ ] 注释和文档是否同步更新

**修复**：
- 发现的问题逐条修复
- 修复后重新运行步骤 4 的测试
- 审查通过后再进入下一步

// turbo
## 步骤 6：Git 提交与推送（Commit & Push）

代码审查通过后，执行 Git 操作：

1. **确认变更**：
   ```bash
   git status
   git diff --stat
   ```

2. **提交**：
   ```bash
   git add -A
   git commit -m "V{x}.{y}.{z}: {简短描述}
   
   - {变更点 1}
   - {变更点 2}
   - ..."
   ```

3. **打标签**（如果是里程碑版本）：
   ```bash
   git tag V{x}.{y}.{z}
   ```

4. **推送**：
   ```bash
   git push origin main
   git push origin V{x}.{y}.{z}  # 如有标签
   ```

> **注意**：提交前确保测试全部通过，不要提交带有 `TODO` 或 `FIXME` 的代码。

---

## 禁止事项

- 不要跳过 prompt-master 优化步骤
- 不要在测试未通过时提交代码
- 不要擅自扩大需求范围
- 不要在工作流中引入计划外的技术债务
